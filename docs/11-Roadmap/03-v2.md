# Visão Geral

Este documento define a direção estratégica e arquitetural da **Versão 2 (v2)** do MedFlow.

A v2 representa a fase de expansão estruturada da plataforma após a consolidação promovida pela v1.

A evolução conceitual será:

```text
MVP

↓

Validate Value

↓

v1

↓

Consolidate Product

↓

v2

↓

Expand Platform
```

Enquanto o MVP responde:

```text
Does MedFlow solve
a real healthcare problem?
```

e a v1 responde:

```text
Can organizations
depend on MedFlow?
```

a v2 deverá responder:

```text
Can MedFlow support
more organizations,
more workflows,
more integrations
and more intelligence
without losing control?
```

O objetivo da v2 não será simplesmente tornar o MedFlow maior.

Será tornar o MedFlow uma **plataforma extensível**.

---

# Princípio Central

A v2 deverá seguir:

```text
Expand capabilities

without

expanding chaos.
```

Crescimento deverá preservar:

- Security.
- Privacy.
- Reliability.
- Maintainability.
- Tenant Isolation.
- Auditability.
- Performance.
- User Experience.
- Architectural Coherence.

---

# Pré-Requisitos

A v2 pressupõe que a v1 tenha alcançado maturidade suficiente.

Antes de iniciar grandes iniciativas da v2 deverão existir evidências sobre:

- Product-Market Fit inicial.
- Core Workflow Stability.
- Customer Retention.
- Operational Reliability.
- Security Maturity.
- Infrastructure Cost.
- AI Usage.
- Integration Demand.
- Commercial Patterns.
- Organization Growth.

---

# v2 Is Not Automatic

A existência deste Roadmap não significa que todas as Features descritas deverão ser implementadas.

```text
Roadmap

≠

Promise
```

Cada iniciativa deverá ser reavaliada quando sua implementação estiver próxima.

---

# Evidence Gate

Toda iniciativa significativa deverá responder:

```text
What problem exists?

Who has this problem?

How frequently?

What is the impact?

What evidence exists?

Why now?

Why v2?
```

# Objetivos da v2

A v2 deverá permitir que o MedFlow evolua para uma plataforma capaz de:

- Atender organizações maiores.
- Suportar workflows mais complexos.
- Integrar sistemas externos.
- Automatizar tarefas recorrentes.
- Expandir AI Assistance.
- Melhorar Analytics.
- Suportar estruturas Multi-Unit.
- Melhorar Collaboration.
- Aumentar configurabilidade.
- Melhorar Developer Experience.
- Expandir capacidade de integração.
- Aumentar resiliência operacional.

---

# Não Objetivos

A v2 não deverá automaticamente:

- Migrar tudo para Microservices.
- Criar infraestrutura global sem demanda.
- Implementar todas as especialidades médicas.
- Construir Marketplace completo.
- Criar linguagem de programação interna.
- Tornar toda regra configurável.
- Substituir todos os sistemas hospitalares.
- Criar AI autônoma para decisões clínicas.
- Eliminar Human Oversight.

# v2 Exit Criteria

- Multi-Unit estiver seguro quando implementado.
- Authorization suportar complexidade necessária.

- AI Platform possuir Governance.
- Automations forem auditáveis.
- Integration Layer estiver observável.

- Reliability possuir SLOs apropriados.

- Internationalization Foundation estiver preparada quando necessária.

Service Extraction exigirá justificativa baseada em Scaling, Deployment, Failure Isolation, Security Boundary ou Ownership.

Cross-Unit Access deverá ser controlado explicitamente por Authorization.

# Considerações Finais

A v2 representa uma mudança importante na história do MedFlow.

Até aqui, a pergunta principal era:

```text
Can we build a good healthcare product?
```

Na v2, a pergunta passa a ser:

```text
Can we build a healthcare platform
that grows without becoming fragile?
```

Essa diferença é fundamental.

É relativamente fácil adicionar Features.

É muito mais difícil criar uma plataforma onde novas Features possam ser adicionadas durante anos sem transformar o sistema em um conjunto imprevisível de dependências.

Por isso, a v2 deverá investir não apenas no que os usuários veem.

Também deverá investir no que futuros desenvolvedores precisarão.

```text
Boundaries

Contracts

Events

Policies

Observability

Automation

Documentation
```

O sucesso da v2 não deverá ser medido pelo número de módulos existentes.

Deverá ser medido pela capacidade de adicionar o próximo módulo sem quebrar os anteriores.

```text
Good Platform

=

Stable Core

+

Clear Boundaries

+

Reusable Capabilities

+

Controlled Extension
```

A arquitetura deverá continuar resistindo à tentação de complexidade prematura.

Microservices.

Event Streaming.

Data Warehouses.

AI Agents.

Multi-Region.

Enterprise Identity.

Todas essas tecnologias podem se tornar úteis.

Nenhuma delas será automaticamente necessária.

A pergunta continuará sendo:

```text
What problem does this solve
for MedFlow now?
```

Se não houver uma resposta clara, a tecnologia poderá esperar.

A v2 deverá preparar o MedFlow para crescer.

Mas deverá fazer isso sem esquecer a principal regra que permitiu chegar até aqui:

```text
Complexity must be earned.
```

Quando a v2 estiver consolidada, o MedFlow deverá estar preparado para uma nova fase.

Não apenas um produto.

Não apenas uma plataforma.

Mas potencialmente um ecossistema.

Essa será a responsabilidade de:

```text
04-v3.md
```
